# Mix & Match on iPad

A test build. One screen — the Timer tab — running on real glass, so you can
find out how the round clock and the arcade feel under a thumb.

**It needs no Mac.** Swift Playgrounds on iPadOS builds, signs and runs it on
the device itself.

---

## Get it on the iPad

You need: an iPad with **Swift Playgrounds 4.4 or later**, **Developer Mode**
on (Settings → Privacy & Security → Developer Mode), and an Apple ID. A paid
Developer Program membership is not required to run it on your own device — it
is required for TestFlight and the App Store.

1. On the iPad, download this repository's branch as a ZIP from GitHub, or
   AirDrop the `MixMatch.swiftpm` folder over from another machine.
2. Unzip in **Files**. `MixMatch.swiftpm` will show up as a single Swift
   Playgrounds document rather than a folder.
3. Tap it. Swift Playgrounds opens it.
4. Press **▶︎ Run**. First run asks you to pick a signing team — choose your
   Apple ID or the developer team.

To leave it on the home screen after you stop debugging, use the **⋯ → App
Store Connect** flow, or open the same package in Xcode on a Mac and install
via a development profile. A run from Playgrounds is a development build and
expires the way all development builds do.

### Not a Mac? Not a problem — but know the ceiling

Swift Playgrounds can build, run and even upload to App Store Connect. What it
cannot do is run the XCTest suite in `../swift`, attach Instruments, or drive a
CI build. Those want Xcode. Nothing in this app needs them yet.

## What is actually in here

```
MixMatch.swiftpm/
  Package.swift          the app product. PLAYGROUNDS ONLY — see below
  MixMatchApp.swift      @main, one window, dark
  WebHost.swift          WKWebView + a URL scheme handler
  Resources/index.html   GENERATED from ../../web — do not edit
```

`Package.swift` imports `AppleProductTypes`, which ships inside Swift
Playgrounds and does not exist in plain SwiftPM or Xcode. `swift build` on this
directory fails on purpose. The package CI compiles is `../swift`
(MixMatchKit), which is deliberately free of UIKit so it builds on Linux.

### Why a WebView and not a SwiftUI rewrite

The same reasoning as `rocketman/android`: the expensive part is already
written and tested. `mixmatch/web/timer-engine.js` has 48 tests behind it,
including a heuristic player that proves the game's balance holds over a
twelve-minute round. Rewriting the clock and the arcade in SwiftUI means
maintaining the rules twice and diffing them forever.

`MixMatchKit` exists for the part that genuinely must be native: the token
arithmetic behind an eventual StoreKit purchase. Logic deciding what a customer
is charged does not belong in a web page inside a wrapper.

### Why a custom URL scheme instead of `loadFileURL`

A `file://` page in WKWebView gets an opaque origin, and an opaque origin has
no dependable `localStorage`. The Timer tab keeps your preset, your sound
preference and your best score there. Registering a scheme handler gives the
page a real, stable origin so those survive a relaunch.

This is the same problem `GameAssetServer.java` solves on Fire OS by running a
loopback HTTP server. WebKit has a first-class answer, so there is no socket
here and nothing listening on a port.

`index.html` is generated by `npm run mixmatch:timer` from the same block that
gets pasted into `MixMatch.html`. CI fails on a stale copy. **Do not edit it in
Playgrounds** — the edit will be overwritten, and the app would drift from the
web app, which is the whole thing this pipeline exists to prevent.

## Before this can be a real App Store app

### Purchases must go through StoreKit

Apple requires in-app purchase for digital content (Guideline 3.1.1). The $15
token pack and the $5/mo subscription therefore cannot open a Stripe page on
iOS. That means products in App Store Connect, a StoreKit 2 flow, and — the
part people skip — **server-side receipt verification before granting credit**.
The broker must not take the client's word that a purchase happened.

**Real-world services are the exception.** Guideline 3.1.3(e)/3.1.5 exempts
goods and services consumed outside the app, which is what a live Practice Lab
seat is. A $350 cohort seat can stay on Stripe. Do not conflate the two in one
checkout screen.

### The 15% is already in the numbers

`mixmatch/config/tokens.js` carries both rails and what each nets:

| | Stripe | Apple (15%) | given up |
|---|---|---|---|
| $15 pack | $14.26 | $12.75 | **$1.51** |
| $5/mo | $4.55 | $4.25 | **$0.30** |

Worth knowing before deciding which rail to nudge people toward: Stripe's 30¢
flat fee is most of the fee on a $5 charge, so at subscription size the two
rails are within pennies. On the pack they are not.

The 15% is the **Small Business Program** rate — under $1M of proceeds a year.
Enrollment is annual and can lapse; if it does, `RAILS.apple_iap.feeBps`
becomes 3000 and every figure above moves. That constant is asserted in both
the JavaScript and the Swift suites so the change cannot pass unnoticed.

### Other things App Review will want

- A privacy policy URL, and an accurate privacy "nutrition label". Today the
  app collects nothing and makes no network requests, which is the easiest
  possible version of that form — keep it that way as long as you can.
- An app icon. `Package.swift` currently uses `.placeholder(icon: .timer)`,
  which is fine for a test build and not for submission.
- Something to actually review. A single timer is thin for the App Store on its
  own; ship it as part of Mix & Match rather than as a standalone.

1. **Play it on the iPad.** That is what this build is for. If the arcade is

2. **Point the WebView at the real Mix & Match** instead of the bundled page,

4. **StoreKit**, only if 1–3 say the app is worth shipping.
